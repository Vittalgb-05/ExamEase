2. Django MVT (Model - View - Template) Explained with ExamEase Examples

Django follows the MVT architectural pattern (a variant of MVC). In MVT, the framework itself acts as the Controller:

1. MODEL (Data Layer)

Python classes defining database tables, fields, and constraints.

Example in ExamEase:
class Attempt(models.Model) defines fields like deadline, score, tab_switches, and relationships via ForeignKey(Exam).

2. VIEW (Business Logic)

Python functions processing HTTP requests and returning HTTP responses.

Example in ExamEase:
def attempt_save(request, pk) validates the attempt, checks deadlines, saves the answer atomically, and returns a JsonResponse.

3. TEMPLATE (Presentation)

HTML files with Django Template Language (DTL) tags ({% %}, {{ }}).

Example in ExamEase:
exam_take.html renders the questions, options, countdown bar, and loops through {% for q in questions %}.

3. Key Django ORM Concepts (Frequently Asked in Interviews)

⚡ select_related vs prefetch_related
  • select_related (SQL INNER JOIN): Used for single-valued relationships (ForeignKey, OneToOne). Executes 1 single SQL query using an SQL JOIN.
    ExamEase usage: Attempt.objects.select_related("exam", "student") – fetches the attempt, its exam, and student in one roundtrip.
  • prefetch_related (Separate Queries with 'IN'): Used for multi-valued relationships (ManyToMany, reverse ForeignKey). Executes 2 queries and joins in Python memory.
    ExamEase usage: exam.questions.prefetch_related("choices") – fetches questions, then loads all choices in a second query. Prevents N+1 query problems!
🔒 Unique Constraints & Atomicity
  • Why UniqueConstraint? In Attempt, UniqueConstraint(fields=["exam", "student"]) guarantees at the database level that a candidate can NEVER take an exam twice, preventing race conditions.
  • Why transaction.atomic()? Used during finalization (attempt.finalize()). Either all answers are evaluated and the attempt is marked submitted, or the entire operation rolls back if the server crashes.
  • Migrations: makemigrations inspects models and generates Python migration scripts; migrate translates them into raw SQL (CREATE TABLE, ALTER TABLE) and tracks applied migrations in django_migrations.

4. Deep-Dive into Core Features (Under the Hood)

1. Authentication & Role-Based Access Control (RBAC)

ExamEase implements custom authentication and strict authorization using custom decorators:

Custom User Model & Role Field

Instead of Django's default User, ExamEase extends AbstractUser in core/models.py:

class User(AbstractUser):
  role = models.CharField(max_length=10, choices=[('teacher', 'Teacher'), ('student', 'Student')])

This enables single-table inheritance with fast role checks: user.is_teacher and user.is_student.

Role Decorator Pattern (views.py)

Protected views use a higher-order Python decorator:

def role_required(role):
  def decorator(view):
    @login_required
    def wrapper(request, *args, **kwargs):
      if request.user.role != role:
        return redirect("dashboard")
      return view(request, *args, **kwargs)
teacher_required = role_required("teacher")

2. Classroom Cohort System & Join Code Generation

To eliminate manual enrollment while keeping cohorts private, teachers generate unique 6-character codes:

  • Generation Algorithm: A custom utility generates a 6-character alphanumeric string avoiding ambiguous letters (e.g. I, O, 1, 0):
    def _new_class_code(): return "".join(secrets.choice("23456789ABCDEFGHJKLMNPQRSTUVWXYZ") for _ in range(6))
  • Collision Avoidance: A while ClassRoom.objects.filter(code=code).exists() loop guarantees uniqueness before saving to PostgreSQL.
  • Student Joining: Candidate submits code → JoinClassForm validates code → Enrollment.objects.get_or_create(classroom=class, student=request.user) adds the student without duplicating records.

3. The Live Examination Cockpit (High-Value Interview Topic)

⏱️ Continuous Server-Side Authority Timer

The Interview Problem: "If a student pauses JavaScript, disables their network, or changes their laptop clock, do they get extra time?"

The ExamEase Solution: NO. When an exam starts, Django records attempt.deadline = min(now + duration, exam.end_time) directly in the database.

When the candidate submits or sends an autosave, Django checks now > attempt.deadline + grace_seconds. If expired, Django immediately rejects the answer and calls attempt.finalize(). The browser JS countdown is strictly for visual presentation.

💾 Real-Time Asynchronous Autosave

How it works: Whenever a student clicks an option radio button, vanilla JavaScript triggers an event listener:

  1. JS reads question ID and choice ID.
  2. Sends an asynchronous fetch() POST to /attempt/<id>/save/.
  3. Includes X-CSRFToken in HTTP header.
  4. Django validates ownership and deadline, updates/creates Answer row.
  5. Returns {"ok": true} → UI displays green "Saved" status pill and turns palette dot blue.
🔀 Deterministic Question Shuffling

How it works: Cheating prevention requires different students to see different question orders, but refreshing the page must NOT change the order for the same student!

Solution: Seeded pseudo-randomness:

random.Random(attempt.pk).shuffle(questions)
random.Random(attempt.pk * 100003 + q.pk).shuffle(options)

Because the seed is based on attempt.pk (which is unique to that student session), the shuffle order is 100% deterministic and permanent across reloads.

👀 Tab-Switch Telemetry (Cheating Detection)

How it works: The browser listens for HTML5 Page Visibility API events:

document.addEventListener('visibilitychange', () => {
  if (document.hidden) { sendBeacon('/tab-switch/'); }
});

Whenever the candidate switches tabs or minimizes the browser, an increment request is sent to the server. The teacher's results table flags candidates with >0 tab switches with an amber warning badge.

4. Automatic Grading & Atomic Finalization

How attempt.finalize() Computes Grades
  1. Loads all questions and their choices using prefetch_related("choices").
  2. Maps student's recorded answers from the Answer table.
  3. Iterates through questions: if the student's selected choice.is_correct == True, increments score += question.marks.
  4. Computes percent = round((score / total) * 100, 1).
  5. Determines passed = percent >= exam.pass_percent. Sets submitted_at = now.
  6. Saves inside an atomic transaction block. The attempt is now locked and immutable.

5. Security, Testing, Deployment & Customizations

1. Security Engineering & Vulnerability Defenses

Security Threat How ExamEase Defends Against It Django / Code Mechanism
SQL Injection (SQLi) Never concatenates user strings into raw SQL queries. Django ORM uses parameterized queries (prepared statements) by default for all queries and filters.
Cross-Site Request Forgery (CSRF) Validates cryptographic session tokens on all state-changing POST requests. CsrfViewMiddleware checks {% csrf_token %} in forms and X-CSRFToken headers in AJAX requests.
Cross-Site Scripting (XSS) Prevents user-injected malicious JavaScript in question text or names. Django Template Language (DTL) automatically HTML-escapes all variables ({{ var }}).
CSV Formula Injection Attacker inputs =cmd|' /C calc'!A0 into student names to execute code in Excel. csv_safe() in utils.py prefixes formula characters (=, +, -, @) with a single quote (').
Session Hijacking & Man-in-the-Middle Forces HTTPS and ensures cookies are inaccessible via malicious JavaScript. SECURE_SSL_REDIRECT = True, SESSION_COOKIE_SECURE = True, CSRF_COOKIE_SECURE = True, HTTPOnly flags.
Answer Key Leakage Candidate inspects HTML source to find correct answers during the exam. The exam-taking view (attempt_take) queries only questions and choice text; is_correct is NEVER sent to the template.

6. Top Technical Interview Q&A (Part 1)
Q1. Can you explain your project ExamEase in simple terms?
Answer: "ExamEase is an online examination management platform built with Django, PostgreSQL, and Bootstrap 5. It allows teachers to create classrooms with private 6-character join codes and publish timed MCQ exams. Students join classes, take tests with live countdown timers and real-time autosave, and receive instant scorecards upon submission. Teachers get live leaderboards, individual answer reviews, and Chart.js analytics."
Follow-up: "What was the hardest problem you solved?" → Answer: Ensuring zero data loss during network hiccups and server-side deadline enforcement.
Q2. Why did you choose Django over Flask, FastAPI, or Node.js/Express?
Answer: "Django is 'batteries-included'. For an examination system requiring secure authentication, role-based access control, CSRF protection, an ORM with migrations, and admin governance, Django provides robust, battle-tested solutions out of the box. Building session auth, CSRF, and relational migrations from scratch in Flask or Express would require multiple third-party libraries and increase security risks."
Follow-up: "When would you prefer FastAPI instead?" → Answer: When building high-performance, asynchronous REST APIs or microservices without server-rendered HTML.
Q3. Explain the Django MVT architecture using an example from your project.
Answer: "MVT stands for Model-View-Template. In ExamEase, the Model is Attempt in models.py, which stores student scores and deadlines in the database. The View is attempt_save in views.py, which receives the HTTP POST request, validates user ownership, checks that the deadline has not passed, and updates the database. The Template is exam_take.html, which renders the questions and countdown timer in HTML."
Follow-up: "Who acts as the Controller in MVT?" → Answer: Django framework itself acts as the controller by handling URL routing and dispatching requests.
Q4. What is the difference between select_related and prefetch_related? Where did you use them?
Answer: "select_related is used for single-valued relationships (ForeignKey, OneToOne) and performs an SQL INNER JOIN in a single query. In ExamEase, I used it when loading an attempt: Attempt.objects.select_related('exam', 'student'). In contrast, prefetch_related is used for multi-valued relationships (ManyToMany, reverse ForeignKeys); it runs two separate queries and joins them in Python memory. I used it when loading questions with choices: exam.questions.prefetch_related('choices'). This completely eliminated the N+1 query problem."
Follow-up: "What is an N+1 query problem?" → Answer: When loading 10 questions causes 1 query for questions + 10 separate queries to fetch choices for each question.
Q5. How does user authentication and role-based authorization work in ExamEase?
Answer: "I extended Django's AbstractUser to add a role field with 'teacher' and 'student' choices. For authorization, I implemented a custom decorator @role_required(role) that wraps views. When a student tries to access a teacher URL like /exams/new/, the decorator checks request.user.role, displays an error message, and redirects them to their student dashboard."
Follow-up: "Why extend AbstractUser instead of AbstractBaseUser?" → Answer: AbstractUser keeps default fields (username, password, email) and adds new fields easily.
Q6. How does the live exam timer work? What happens if a student changes their computer clock?
Answer: "The timer has strict server-side authority. When the exam starts, Django records attempt.deadline = now + duration in PostgreSQL. The JavaScript timer in the browser is purely visual. When the student submits or sends an autosave, Django compares current server time against attempt.deadline. If the student changes their local computer clock, it has zero effect because the server validates its own clock."
Follow-up: "What if there is network latency during submission?" → Answer: I added a 15-second grace period (SUBMIT_GRACE_SECONDS = 15) for network latency.
Q7. How does the autosave feature work without reloading the page?
Answer: "Every radio button has an onchange event listener. When clicked, vanilla JavaScript extracts the question ID and choice ID, and makes an asynchronous fetch() POST request to /attempt/<id>/save/. The request includes the CSRF token in the headers. On the backend, Django validates that the attempt is active, creates or updates the Answer row, and returns a JSON response. The UI then updates the question dot on the palette to blue (answered)."
Follow-up: "What if the student clicks options very rapidly?" → Answer: We debounce requests or rely on Django's UniqueConstraint(attempt, question) to update existing rows.
Q8. What happens if a student refreshes their browser or loses internet connection during the exam?
Answer: "If they refresh the browser, their selections are 100% preserved because answers are already stored in the database. When exam_take reloads, it queries saved answers and checks the matching radio buttons. The timer resumes with the remaining server time. If they lose internet connection, the server timer continues running; if time expires while disconnected, the background helper grade_overdue() grades their saved answers upon their next visit."
Follow-up: "How do you ensure question order doesn't change on refresh?" → Answer: Seeded deterministic shuffling: random.Random(attempt.pk).shuffle(questions).
Q9. How do you prevent a student from attempting the same examination twice?
Answer: "At the database level, the Attempt model defines a unique constraint: models.UniqueConstraint(fields=['exam', 'student'], name='unique_exam_attempt'). At the view level in exam_start, Django checks Attempt.objects.filter(exam=exam, student=request.user).first(). If an attempt already exists, the student is redirected to their existing test or result scorecard."
Follow-up: "Why enforce this at both database and view levels?" → Answer: Defense-in-depth. Database constraints prevent race conditions from duplicate parallel requests.

7. Top Technical Interview Q&A (Part 2 - Advanced)
Q10. How does Django ORM prevent SQL Injection attacks?
Answer: "Django ORM automatically uses parameterized queries (prepared statements). When I write Exam.objects.filter(title=user_input), Django sends the SQL query structure and the user input separately to the database engine. The database treats the input strictly as literal data, never as executable SQL code, completely neutralizing injection attacks."
Follow-up: "Can SQL injection still happen in Django?" → Answer: Yes, only if a developer bypasses the ORM using raw() or extra() with unsanitized string formatting.
Q11. What is CSRF and how did you protect both standard forms and AJAX calls?
Answer: "CSRF (Cross-Site Request Forgery) occurs when a malicious site tricks an authenticated user's browser into executing unwanted actions on another site. Django defends against this using CsrfViewMiddleware. In HTML forms, I included {% csrf_token %}, which outputs a hidden input with a signed token. For AJAX calls in autosave, JavaScript reads the CSRF cookie and passes it in the X-CSRFToken request header."
Follow-up: "Why did you add CSRF_TRUSTED_ORIGINS in settings.py?" → Answer: Django 5 requires HTTPS origin validation to prevent cross-origin POST attacks on cloud domains.
Q12. What is CSV Formula Injection and how did you prevent it?
Answer: "If a student registers with a name starting with formula triggers like =cmd|' /C calc'!A0 or +SUM(...), Microsoft Excel will execute that formula when the teacher opens the exported results CSV. In core/utils.py, I implemented a sanitizer function csv_safe() that checks if the string starts with =, +, -, or @, and prepends a single quote (') to force Excel to treat it as plain text."
Follow-up: "Where else can injection attacks occur?" → Answer: In HTTP headers, file uploads, and template contexts without escaping.
Q13. How does Django handle sessions under the hood?
Answer: "Django uses database-backed sessions by default. When a user logs in, Django generates a 32-character random session key, stores the serialized user session data in the django_session table, and sends a cookie named sessionid to the client. The browser sends this cookie on subsequent requests. In production, I enabled SESSION_COOKIE_SECURE = True so the cookie is only transmitted over HTTPS."
Follow-up: "What is the difference between session storage and JWT?" → Answer: Sessions are stateful (stored in DB); JWTs are stateless (payload signed cryptographically).
Q14. What is the difference between null=True and blank=True in Django models?
Answer: "null=True is a database-level setting: it configures the database column to accept NULL values. blank=True is a form-validation-level setting: it allows the field to be left empty in forms and admin. For string fields like CharField, Django conventions suggest avoiding null=True and using empty strings "" instead to avoid having two representations of 'no data'."
Follow-up: "Where did you use null=True?" → Answer: In Exam.classroom, because an exam can optionally have no classroom restriction (public).
Q15. What is the role of Gunicorn and WhiteNoise in your deployment?
Answer: "Django's built-in runserver is single-threaded and intended strictly for local development. In production on Render, I used Gunicorn as a pre-fork WSGI HTTP server to handle concurrent worker processes. For static files, Django does not serve static files in production (DEBUG=False); WhiteNoise integrates into the Django middleware stack, serving compressed (Gzip/Brotli) and cached static CSS and SVG assets directly from the application without needing an external S3 bucket or Nginx."
Follow-up: "Why not use Nginx?" → Answer: In modern PaaS containers (like Render or Heroku), WhiteNoise provides zero-cost, self-contained static file delivery.
Q16. If 10,000 students take an exam simultaneously, where will the system bottleneck and how would you scale it?
Answer: "The primary bottlenecks would be: 1. Database Writes: 10,000 students clicking options creates 10,000 frequent autosave writes. Solution: Use Redis as a high-speed in-memory cache to buffer autosaves, then flush answers to PostgreSQL asynchronously using Celery background workers. 2. WSGI Concurrency: A few Gunicorn workers would queue requests. Solution: Scale horizontally with multiple container instances behind a load balancer. 3. Database Reads: Solution: Cache exam questions and choices in Redis because question text does not change during an active exam."
Follow-up: "What is Celery?" → Answer: An asynchronous distributed task queue used in Python to offload background jobs from the request-response cycle.
Q17. What was the most difficult bug you encountered and how did you resolve it?
Answer: "During automated browser testing with Chromium, teacher form submissions suddenly triggered unexpected logout redirects. Upon debugging the DOM, I discovered that document.querySelector('form') was matching the hidden logout form in the navbar dropdown instead of the main page form. I resolved this by refactoring selectors to target inputs specifically using input.closest('form').submit(). It reinforced the importance of unambiguous DOM selectors and end-to-end browser testing."
Follow-up: "What did that teach you about testing?" → Answer: Unit tests test logic in isolation, but end-to-end browser tests catch DOM and layout integration issues.
Q18. What limitations does ExamEase currently have and what features would you build next?
Answer: "Currently, ExamEase supports Multiple Choice Questions (MCQs) exclusively. Limitations and future enhancements include: 1. Subjective & Code Questions: Adding support for short answers and automated code execution using Docker sandboxes. 2. AI Proctoring: WebRTC camera monitoring to detect multi-face or gaze divergence. 3. Question Bank Import: Bulk question uploading via Excel or JSON templates. 4. Real-Time WebSockets: Using Django Channels to push live submission updates to the teacher dashboard without page refresh."
Follow-up: "What is Django Channels?" → Answer: An extension that allows Django to handle WebSockets and asynchronous protocols.

Snippet 2: Atomic Finalization & Grading (core/models.py)
@transaction.atomic
def finalize(self, now=None):
  if self.is_submitted: return
  answers = {a.question_id: a.choice for a in self.answers.all()}
  score = 0
  for q in self.exam.questions.all():
    picked = answers.get(q.pk)
    if picked and picked.is_correct:
      score += q.marks
  self.score = score
  self.percent = round((score / self.total) * 100, 1)
  self.passed = self.percent >= self.exam.pass_percent
  self.submitted_at = now or timezone.now()
  self.save()
